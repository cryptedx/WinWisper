# Translate with a dedicated offline machine-translation model

WinWispr translates between German and English with a dedicated, local machine-translation model, one model per direction. It does not use a cloud translation service and it does not use the local language model that is being evaluated for transcript cleanup. Speech recognition and speech output already run fully offline, and sending dictated or selected text to a third party would break that guarantee for enterprise users. A small cleanup-sized language model translates noticeably worse, and a larger one costs far more memory and latency, while a dedicated German-English model is fast and built for exactly this pair.

A translation never takes longer than three seconds. That requirement shapes the engine: it rules out beam search and long selections, and it decides when the model loads. Run the latency gate in `docs/testing/windows-11-acceptance.md` ("Latency gate") before any change of the selection limit or the engine tuning.

## Considered options

- **Cloud translation (for example DeepL or OpenAI):** best quality, but it needs network access, an API key and a paid account, and it sends user text off the machine. Rejected.
- **Local language model shared with transcript cleanup:** one runtime for both jobs, but small models translate poorly, large ones are expensive, and the cleanup evaluation is not finished. Rejected.
- **Translation inside the speech recognizer (a speech-to-English translate task):** handles dictation only, not selected text. Rejected.
- **Firefox Translations `base-memory` through Bergamot:** published scores put it level with the chosen model for German to English and about two COMET points ahead for English to German, and it is much smaller. It needs a native library without an official Windows build, and its model files sit in a bucket whose paths can change. It was not run and stays the fallback if the quality of the chosen model proves insufficient in use.
- **A larger Opus-MT model for English to German (`opus-mt-tc-big`):** exists only as a 619 MB fp32 PyTorch file with no ONNX export, and it was not exported, sized or evaluated. It is the documented upgrade path if English to German quality proves to be the weak spot.

## Chosen model

Helsinki-NLP Opus-MT (`opus-mt-de-en` and `opus-mt-en-de`) as int8 ONNX exports, run on the ONNX Runtime that WinWispr already ships, with greedy decoding in both directions. It was qualified on the Windows build host with the speech model resident in the same process.

- **Viable.** Both directions load and run on the shipped ONNX Runtime 1.24.4 through its managed binding, every operator they need is available, and the .NET tokenizer reproduces the reference token ids and detokenization. With greedy decoding on two threads on a shared, loaded machine a dictation-length sentence takes about 0.6 seconds and about 100 tokens (roughly 450 characters) take about 3 seconds. One direction loads in about 2 seconds and adds about 0.45 GB of private memory once used.
- **Quality.** On 12 frozen held-out cases per direction, rated blind by two raters, no translation changed a negation, number, date, unit or name in the sense of the rating rubric. Every setup, including the fp32 reference, reached only 8 or 9 of 12 usable against an original gate of 11, so quantization is not the cause; the gaps are terminology, idioms and, in whole-text mode, a dropped sentence. The maintainer lowered the gate to no factual error and at least 9 of 12 usable, after the results were known. Greedy decoding meets it for German to English (9 of 12) and misses it by one case for English to German (8 of 12; one rater gave 11), which the maintainer accepted for speed. Beam search reached 9 of 12 for English to German but is 1.7 to 1.9 times slower (5,000 characters took 38 to 51 s) and was dropped.
- **Latency.** The three-second requirement is targeted by construction and checked by measurement: greedy decoding, a selection length limit derived from measurement, parallel segments, and loading the model when the need is known (at the press of the English dictation hotkey, or right after a selection is read and its language detected) instead of on the critical path. A safety deadline turns an overrun into a failure. Dictation translation has no length limit, because spoken content must never be dropped; a very long dictation takes proportionally longer.
- **Throughput (measured on the Windows build host, a 6-core ARM VM running x64 emulated, with the speech model resident).** The text is split into sentences and chunks of at most 128 tokens, and one segment per core (up to six) is decoded in parallel through the shared sessions. Padded batches of several segments through one decoder pass were measured too and rejected: dynamic int8 quantization scales activations per tensor, so a batch changes some outputs against sentence-by-sentence translation, while parallel segments keep every output identical. The decoder stores the shared embedding as int8 and dequantizes it to a 119 MB float matrix in every step of every run; setting the session option `session.disable_quant_qdq` to 1 lets constant folding do that once at load. It gave byte-identical outputs, 1.6 times the speed and no extra memory per concurrent run (without it, each concurrent run added about 120 MB). With both, 5,000 characters take 2.0 s (German to English) and 2.5 s (English to German) on a warm model, 7,200 characters 3.3 s, and one direction adds about 0.4 to 0.5 GB of private memory once used (limit 0.6 GB). The selection length limit was 5,000 characters, then 4,000 (end-to-end runs including the preview exceeded three seconds at 5,000), and is now 3,000 (the latency gate at 4,000, unpunctuated English to German, took 3.06 to 3.62 s); the measurement and its procedure are in `docs/testing/windows-11-acceptance.md`.
- **License.** The upstream project states CC BY 4.0 for the models, and its Hugging Face page for the German to English model is tagged Apache-2.0. Both permit commercial redistribution; WinWispr follows the upstream statement. CC BY 4.0 requires attribution, a license reference and a statement of the changes (ONNX conversion and quantization).
- **Packaging.** Ten files, five per direction (the two int8 graphs, the two SentencePiece models and the vocabulary, about 218 MB in total), shipped in Setup and Portable as loose files in `TranslationData` next to the executable and read there in place. The package build takes them from a local build input and copies each file only after it matches its pinned size and SHA-256; the model-free Update does not contain them and leaves an installed copy alone. The model was first an optional download from Settings, file by file from the public Hugging Face locations at pinned commits (a mirrored archive in the project's private repository was dropped because anonymous downloads of its release assets fail). That was replaced on 2026-10-08: managed work networks block the download, so translation never became available where it is needed most, and a download is a network exception that every enterprise review has to approve. Bundling makes Setup and Portable about 200 MB larger, which is accepted.

## Consequences

- The translation model is part of Setup and Portable, so translation works offline right after installation and WinWispr makes no network request for it. Every user pays its size, whether they translate or not.
- An installation that was only ever updated with the model-free Update has no model: the features that need it report that translation is not installed, Settings says the model is missing, and running Setup restores it.
- Adding another language pair means another model per direction.
- Selection translation accepts only short selections (the limit follows from the measured three-second throughput) and reports the limit when a selection is too long.
- The translation is useful but uneven. Terminology and idioms can be wrong, a technical term, a condition or a product name can change, a clause can be garbled and a sentence can be left out. Selection translation lets the user check the result in a preview before replacing anything; dictation translation pastes directly, so the user documentation tells users to review it.
- The evidence is small (12 cases per direction, one case is eight points), the gate was lowered after the results were known, and the gate was measured on whole texts while the product translates sentence by sentence. The acceptance tests cover the sentence-by-sentence path on fixed inputs. A change of model or of the translation settings is qualified again against the same frozen synthetic cases and rubric, and a new model's license attribution goes into the third-party notices and the enterprise security document.
